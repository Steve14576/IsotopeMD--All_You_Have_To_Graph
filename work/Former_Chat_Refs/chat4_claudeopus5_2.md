## 一、先看这五个工具的本质差异

| 工具 | 流的是什么 | 执行模型 | 时间模型 | 确定性 |
|------|----------|---------|---------|--------|
| Grasshopper | 几何/数值数据 | 拉取式DAG重算 | 无时间/瞬时 | 确定 |
| Scratch | 消息/事件 | 推送式事件循环 | 离散事件 | 确定 |
| Simulink | 信号 | 求解器驱动 | 连续时间 | 确定（可含随机块） |
| LangGraph | 状态对象 | 条件路由+循环 | 异步/挂起-恢复 | **非确定**（LLM） |
| Obsidian | 语义链接 | 无执行，纯索引 | 无 | N/A（不是计算图） |

**关键洞察**：前四个都是"计算图"，Obsidian是"知识图"——它的边不是数据流，是**语义关系**。这是你整合时最大的坎：Obsidian的节点是惰性的（笔记不会自己跑），要把它塞进一个执行引擎里，得给笔记赋予"可被查询/可被节点读取"的能力，而不是让它变成可执行节点。

## 二、已经有人在往这个方向摸索了（别从零开始）

- **Houdini** — 最接近的现有范式。它用"多context节点网络"（SOP/DOP/VOP等）共享同一套节点基础设施，但不同网络语义不同。这就是你要的"域插件"思路的现实证明。
- **Unreal Blueprint** — 同一张图里混合事件驱动（Event Graph）和数据流（纯函数节点），证明离散事件+dataflow能在一个kernel里共存。

- **Obsidian Canvas** — Obsidian自己已经在往"通用节点画布"进化了，社群插件（如Advanced Canvas）已经有人在上面跑执行逻辑。这可能是你**最现实的切入点**，不用重写笔记那一层。

## 三、如果真要做，架构大概这么分层

```
┌─────────────────────────────────────┐
│  UI层：统一画布 + 多视图切换           │  ← 几何预览/波形示波器/对话轨迹/知识图谱
├─────────────────────────────────────┤
│  域插件层：几何核/信号块/事件块/Agent节点 │
├─────────────────────────────────────┤
│  类型系统：Number/Geometry/Signal/     │
│           Text/Link/AgentState        │
├─────────────────────────────────────┤
│  多调度器执行引擎（核心难点）           │
│  - Pull调度器（Grasshopper式）        │
│  - Push调度器（Scratch式）            │
│  - 连续时间求解器（Simulink式）        │
│  - 挂起/恢复状态机（LangGraph式）      │
├─────────────────────────────────────┤
│  统一图内核：节点/端口/边 + 元数据      │
├─────────────────────────────────────┤
│  存储层：diff-friendly序列化（类Obsidian）│
└─────────────────────────────────────┘
```

**最难的三个技术坑**：

1. **连续时间 vs 离散事件的统一**——Simulink要ODE求解器，Scratch/LangGraph是事件/状态跳转，数学模型根本不同，通常只能靠"接口转换节点"桥接，不能真正融合成一个调度器。

2. **LLM节点的异步/非确定性**——普通节点跑完立刻出结果，LLM节点要等API、可能要人工介入（human-in-the-loop）。这要求你的**调度器内核必须支持任意节点的挂起与恢复**（这正是LangGraph checkpoint机制存在的原因）。这个能力最好从底层就设计进去，不要后加。

3. **笔记节点的语义**——Obsidian的双向链接是查询产物，不是执行产物。如果想让它进计算图，得设计"链接节点"为**可查询但不可执行**的特殊类型，和其他节点区分对待，否则整个类型系统会很混乱。

## 四、你面前真正的设计难题不是"整合"，是这一个

### ComfyUI
- **是什么**：AI画图工具Stable Diffusion的节点式操作界面
- **看点**：节点上的插槽（port）会用不同颜色区分数据类型（图像/文本/数字），拖线的时候只有类型匹配的插槽能连上——这是"强类型可视化"的活教材

### Blender 几何节点（Geometry Nodes）
- **是什么**：3D建模软件Blender里，用节点图生成/修改3D模型的功能，跟你提到的Grasshopper是同一类东西（甚至更强）

- **是什么**：游戏引擎Unreal Engine里，不写代码用节点图编程的系统
- **看点**：一张图里同时有"事件触发的线"（白色粗线，代表"这件事发生了然后干那件事"）和"数据流的线"（细线，代表"这个数字传给那个输入"）。**这正好是你需要的"控制逻辑+数据流混合"的活例子**，值得重点截图研究

### n8n / Node-RED
- **是什么**：开源的"自动化流程"节点工具，比如"当邮箱收到新邮件→提取内容→发到微信"，业余爱好者/小公司常用来做自动化
- **看点**：这两个的节点粒度就是"业余向"的（不追求Aspen那种数值精度），跟你要的"打草稿"定位气质很像，值得看它们节点面板长什么样、怎么配置参数

### LabVIEW
- **是什么**：工业界做仪器测控用的图形化编程语言，四十年历史
- **看点**：不用你会用，看几张截图就行，重点看它"数据流+循环结构（For循环、While循环长得像个方框把一堆节点包起来）"的表达方式——这是"图形化编程怎么表达循环"这个具体问题的成熟答案

## 四、协议/标准类思想（这些不是软件，是"设计哲学"，重点看思路）

### Jupyter Notebook
- **是什么**：你可能已经用过或听过，写代码+看结果+写文字混在一个文档里的工具，数据科学圈标配
- **关键设计**：它把"UI+存档格式"和"代码怎么跑"这两件事**分开**了——Notebook只负责"发个消息给后台的Python/R/Julia，等结果，展示出来"，具体怎么算它不管
- **对你的启示**：你的画板同理，UI层不需要知道节点内部在跑python还是在等人手动填数字，只需要定义好"节点怎么收数据、怎么吐数据"的固定接口，内部随便换

### ONNX
- **是什么**：一个"神经网络模型"的通用文件格式，让你在PyTorch训练的模型，能被TensorFlow或别的框架读取
- **关键设计**：它没想统一"怎么训练模型"（那个依然是PyTorch/TensorFlow各自的领域），只统一了"模型长什么样"这个**描述格式**
- **对你的启示**：如果以后你想让别人的Python库节点能塞进你的画板，你需要类似的"这个节点该长什么样"的标准描述（输入几个口、输出几个口、每个口是什么类型），而不需要管库内部代码

### MIDI / USB-C（这个是类比，不是软件）
- MIDI是电子乐器之间通信的标准接口，USB-C是设备供电+传数据的标准接口
- **共同点**：它们统一的是"接口"，不是"设备内部构造"。你的画板如果要接各种"电池"（专业计算模块），也该走这个思路——先定好节点之间怎么"插"，不要管电池内部怎么造

### ROS (Robot Operating System)
- **是什么**：机器人开发的一套软件框架，统一了机器人身上各种硬件模块（摄像头、马达、传感器）之间传消息的方式
- **关键设计**：不同厂家的摄像头、不同算法的路径规划模块，只要都按ROS的消息格式包装一下，就能互相通信，不需要重写彼此内部逻辑
- **对你的启示**：这是"专业模块各自独立发展，靠统一协议粘合"这个思路做得最成功的现实案例之一，值得作为你"以后怎么接Python库当电池"这个问题的参照对象（不用现在学ROS，知道这个思路就够）

## 一、名词上的澄清

**OOP领域最著名的"原教旨主义"之争不是这个。** OOP圈子里被反复吵的经典议题是：

- **继承 vs 组合**（"composition over inheritance"，现在基本已成共识：多用组合）
- **Alan Kay的"真正的OOP是消息传递"** vs C++/Java那种"OOP就是类+继承+封装"——Kay本人多次公开说过大意是"我发明object-oriented这个词的时候，脑子里想的不是C++"，这个算是最接近"原教旨主义之争"的东西
- **贫血模型 vs 充血模型**（数据和行为该不该放在一起）
- **Kingdom of Nouns**（Steve Yegge那篇著名讽刺文，嘲讽Java强迫一切都得是名词/对象，函数不能独立存在）

**你说的"边是否为独立对象"，是图建模/数据建模领域的问题**，不是OOP原教旨主义那场架。但它确实是个真实存在、被反复讨论的设计分歧，只是没有一个响亮的"XX主义"名号。我下面直接讲这个真问题，因为它对你更有用。

## 二、"边该不该是一等公民"——真实的分歧战场

这个分歧最清晰地体现在**图数据库**的两大流派：

### 属性图（Property Graph）——边是一等公民
代表：Neo4j、TigerGraph

边本身是个对象，有自己的ID、自己的类型（label）、自己的属性字典。
```
(小明)-[:替班 {日期:"周三", 时段:"下午", 状态:"已确认"}]->(小红)
```
这条"替班"关系可以自己携带一堆数据。

### RDF三元组——边只是个标签
代表：语义网、SPARQL、知识图谱标准

一切都是 `(主语, 谓语, 宾语)` 三元组，边（谓语）只是个URI标签，**本身不能挂属性**。

如果你想给关系加属性（比如"这次替班是周三下午"），你必须用一个叫 **reification（具体化/物化）** 的技巧：把这条关系本身变成一个节点，再挂三条边上去。这是RDF圈子公认的痛点，笨重且查询复杂。RDF-star就是近年为了缓解这个问题搞出来的扩展。

**这就是最真实的战场**：属性图阵营认为"关系当然该有属性，现实世界就是这样"；RDF阵营认为"保持三元组的极简统一性更重要，能推理、能标准化、能全球互联"。

## 三、这个分歧在其他领域的同构表现

你会发现同一个问题在不同领域反复出现：

**UML/数据库建模**：多对多关系必须建"关联表"（junction table），一旦这个关系需要携带属性（比如"选课"关系要记成绩），关联表就自然变成了一个独立实体。UML里这叫 **association class（关联类）**——本质就是"边升格为节点"。

**ER模型**：Chen最初的ER模型里，relationship就是和entity并列的一等概念；但落到关系数据库实现时，relationship往往退化成外键（边变成节点的属性）。这个"理论上边是一等公民、实现上被降级"的张力，从1976年就存在。

**节点式编程工具**：ComfyUI/Blender那种，边通常只是"从哪个port到哪个port"的纯连接，无属性；但一旦你想在边上加"这条流有延迟""这条流当前的状态是阻塞"，边就必须升格为对象。

**你提到的"直接管道 vs 注册全局变量"**，这其实是另一个维度的问题，更接近**耦合方式**的选择：
- 直接连线 = 点对点、显式、拓扑可见
- 发布订阅/黑板模式（blackboard）= 多对多、隐式、拓扑不可见但极度灵活

这两个在架构界的对应讨论是 **choreography vs orchestration**（编舞式 vs 编排式）、或者事件总线 vs 直接调用。ROS用的就是发布订阅（topic），Node-RED用的是直接连线。

## 四、对你的项目，这个选择意味着什么

这直接决定你的核心数据结构，而且**你的需求已经很明确地指向了某一边**：

回想你自己说过的话：
- "更强调节点之间的**流股和状态层级**"
- "如果哪天控制流要结合'人的心情'"
- "谁替谁，谁在谁不在"

## 一、正式对象用什么数据结构存

**核心原则：正式对象是"引用文本片段的语义记录"，不是"含有文本的对象"。**

```ts
// Layer 1: 内容层——死文本，就是 md，块级存储
interface Block {
  id: BlockId
  text: string              // 原始 md 文本
  parent: BlockId | null    // 黑板上的空间/嵌套归属
  rect: {x, y, w, h}        // 画板位置
}

// Layer 2: 语义层——正式对象，唯一真相源
interface FormalObject {
  id: ObjId
  kind: 'variable' | 'unit' | 'formula' | 'entity' | 'process' | ...
  
  // 关键：不存文本，存指针
  source: {
    blockId: BlockId
    range: [start, end]     // 字符偏移，或用 anchor 见下
  }
  
  // 语义属性（结构化，agent 不能乱改）
  props: {
    name?: string
    dtype?: 'number' | 'string' | 'quantity' | ...
    unit?: UnitExpr
    value?: any
  }
  
  // 你需要的状态机
  status: 'fresh' | 'stale' | 'undefined' | 'manual' | 'error'
  lastEval: timestamp
  
  ports: PortId[]
}

interface Edge {
  id: EdgeId
  from: PortId
  to: PortId
  props: Record<string, any>   // 一等公民，允许挂状态
  status: EdgeStatus
}
```

**为什么必须是"引用"而不是"包含"**：

你之前说的"抓完正式的依旧正式，非正式的依旧不正式"、"层层嵌套"、"孤儿正式对象允许存在"——这些需求全部依赖同一件事：**同一段文本可以被多个语义对象以不同粒度引用**。

比如你写了一行 `流量 Q = 3.5 m³/s`：
- 抓 `Q` → 变量对象
- 抓 `3.5` → 数值对象
- 抓 `m³/s` → 单位对象
- 抓整行 → 赋值语句对象

四个正式对象，一段文本。如果对象"包含"文本，你就得复制四份，然后同步地狱——这正是你担心的"重复项啰嗦死"。引用则天然无重复。

### 关于 range 的一个坑（现在就要解决）

字符偏移在文本被编辑后会失效。用户在 `流量` 前面加两个字，后面所有 range 全错。

**解法：anchor（锚点）机制**，这是所有富文本+批注系统的标准解法（Google Docs、Hypothesis 都这么干）：

```ts
source: {
  blockId: BlockId
  anchor: {
    // 主：稳定 ID（编辑时由编辑器维护）
    tokenIds?: string[]
    // 备：内容指纹（ID 丢失时靠这个重新定位）
    quote: string           // 被抓的文本本身
    prefix: string          // 前 32 字符
    suffix: string          // 后 32 字符
  }
}
```

编辑时优先靠 tokenId 跟随；重开文件/ID 失效时用 quote+prefix+suffix 模糊重定位；实在找不到 → **对象不删除，标记 `status: 'orphan'`**（正好对应你说的"孤儿正式对象允许存在"）。

## 三、agent 能不能直接改后端源文件

**答案：分层授权，不是一刀切。**

| 层 | agent 权限 | 理由 |

- agent 改崩了 → 校验拦下，或者用户一键 undo
- 你的核心图结构永远合法（**invariant 由 API 保证，不由 agent 的自觉保证**）
- agent 的每一步都可审计（正好喂给你规划里的"命令历史面板"）

### 一个能让你放心的现成参照

## 二、直接回答"底层 md，跑的时候编译，跑完落盘 md"

**这个方案会死，且死因很明确。**

它其实是个成熟的架构模式（source of truth = 文本，运行时 = 编译产物），编程语言就是这么干的：`.c` 文件是真相，编译成 AST/机器码跑。

**但它有个前提：编译是单向的，运行时状态不需要写回源文件。**

你的场景恰好违反这个前提：

```
1. 编译：md → 图结构
2. 跑：产生 status(fresh/stale)、中间值、边的状态、求值缓存
3. 落盘：图结构 → md   ← 这一步炸
```

第 3 步要面对：
- **status 是运行时状态**，写进 md 意味着每跑一次，全部 md 文件都被改写，git diff 全是噪声
- **不写进 md**，那下次开机 status 全丢，你的"过期传播"机制形同虚设
- **md → 图 → md 往返不可能无损**：用户的手写排版、注释、空行、他随手画的 ASCII 图，编译时被丢弃，落盘时还不回来。用户会发现"我跑了一次，我的笔记被格式化了"

**更致命的是你自己提的那个问题：改残了怎么办。**

底层是 md 时，用户（或 agent）删掉一个 `##` 标题，你的整个块层级瞬间重组，所有正式对象的归属全部错位，而且**没有任何机制能检测到这是个错误**——因为在 md 的世界观里，删个标题完全合法。

底层是结构化数据时，删块要走 `deleteBlock(id)`，API 会告诉你"这个块被 3 个正式对象引用，确认删除吗"。

**这就是你问的"后端数据会碎掉吗"的答案：底层是 md，就会碎；底层是结构化数据 + md 只是内容层，就不会碎。**

## 一、核心未决项：执行模型（4+5+9 是一个问题）

这是现在唯一真正卡住的东西。

### 你的场景实际需要什么

回看你自己举的例子：

- **人员调度**：A 顶 B 的班 → B 空出来 → B 又可以顶 C → 可能绕回 A。**天然有环。**
- **心情影响控制流**：疲劳 → 效率↓ → 拖延 → 更疲劳。**这是反馈环，系统动力学的标准形态。**
- **Aspen 草稿**：循环物流（回流、循环反应器）**必然有环**。
- **Simulink 草稿**：反馈控制 **必然有环**。

**结论：你必须支持环。** 纯 DAG（Grasshopper / Blender GN / ComfyUI 全是纯 DAG）直接出局。

### 但"支持环"有三种截然不同的实现

| 模型 | 怎么处理环 | 代表 | 适合你吗 |
|---|---|---|---|
| **A. 纯 DAG** | 禁止 | Grasshopper, ComfyUI | ❌ 场景不允许 |
| **B. 离散时间步（tick）** | 环上插一个"延迟"，本 tick 读上一 tick 的值 | Simulink 的 UnitDelay、Scratch 的帧循环 | ✅ **最适合** |
| **C. 不动点迭代** | 反复求值直到收敛 | 电路仿真、Excel 迭代计算 | ⚠️ 需要收敛判据，草稿场景过重 |

**推荐 B**，理由：

1. 它同时解决了"时序"——时序不需要单独设计，**tick 就是时序**
2. 它跟你的"过程即结果"完全吻合：每个 tick 的状态快照序列，本身就是产出（"谁替谁"的历史 = tick 序列）
3. 实现简单：拓扑排序时把 delay 边**剪掉**，剩下的就是 DAG，正常求值
4. Simulink 用了几十年，Scratch 也是这个模型，成熟

### 具体机制

```ts
interface Edge {
  id: EdgeId
  from: PortId
  to: PortId
  delay: boolean      // ← 关键：true 表示"读上一 tick 的值"
  props: Record<string, any>
  status: EdgeStatus
}
```

**规则**：
- 建边时做环检测，如果新边会成环 → **自动提示"这条边设为延迟边？"**（默认 yes，用户可改）
- 求值时：`delay: true` 的边不参与拓扑排序，直接读 `prevState[from]`
- 每个 tick：拓扑排序剩余 DAG → 依次求值 → 快照存入历史

**这一个决定同时解决了 4、5、9 三个问题**，且不需要额外的时序设计。

### 剩下的：推还是拉？

有了 tick 之后，这个问题降级了，但仍要定：

- **全量 tick**（每 tick 重算所有节点）：简单，节点少时够用
- **脏标记增量**（只重算受影响的）：复杂，但大图必须

**建议**：v1 用全量 + `status` 标脏做剪枝（`fresh` 的且上游未变则跳过）。这是两者的中间态，实现成本接近全量，性能接近增量。

## 二、status 传播规则（8，现在定死）

之前只提了概念，这是具体规则：

```ts
type Status = 
  | 'fresh'      // 值有效且最新
  | 'stale'      // 有值但上游变了，未重算
  | 'undefined'  // 无值（悬空输入 / 未求值）
  | 'manual'     // 人手填的，不受上游影响
  | 'error'      // 求值失败
  | 'orphan'     // anchor 丢失，语义对象失去文本依托
```

**传播规则（关键的几条）**：

1. **undefined 是传染的**：任一必需输入为 `undefined` → 输出 `undefined`
2. **manual 是阻断的**：手填值不被上游覆盖，且**向下游传播 `fresh`**（这是"半正式黑板"能跑起来的关键——上游还没定义，我先手填一个值，下游照样能算）
3. **error 是传染的，但携带来源**：`error` 向下游传播时保留 `causedBy: ObjId`，方便定位
4. **stale 只在懒求值时出现**：全量 tick 模式下不会有 stale；只有当用户关闭自动求值时才产生
5. **orphan 不影响求值**：文本没了但语义对象还在，`props` 里的值仍然有效，只是失去了溯源。UI 上标黄，不阻断

**这条规则集是你"允许残缺草稿也能跑"的技术兑现**。之前只说了"允许悬空"，但没说悬空之后图怎么继续跑——答案是 undefined 传染 + manual 阻断。

## 三、图层 / 打组 / 过孔（6+7）

这三个是同一件事：**层级与边界**。

### 先明确：你有两种正交的"分组"需求

| | 用途 | 影响求值吗 | 类比 |
|---|---|---|---|
| **Group（打组）** | 视觉整理、批量移动 | ❌ 不影响 | PPT 的组合、Figma 的 group |
| **Subgraph（子图/容器）** | 抽象封装、复用 | ✅ 影响（有自己的输入输出口） | Blender node group、GH cluster |

**别把它们合成一个。** Grasshopper 的 Group 和 Cluster 就是分开的，这是对的。

### 过孔问题

你问"图层之间能否过孔"——具体到两种分组：

- **Group**：**完全允许穿透**。Group 只是视觉框，边可以随便跨进跨出，因为它对求值不可见。
- **Subgraph**：**不允许穿透，必须走端口**。这是封装的意义所在。

但这里有个你的场景特有的问题：**草稿阶段，用户经常需要"临时拉一条穿透 subgraph 的线"来试试。**

**解法：允许"违规边"存在，但标记为 `violating: true`，UI 上画成虚线/红线。** 求值时仍然生效（草稿优先），但导出/正式化时报警。

这跟你的整体哲学一致：**不阻止用户做不规范的事，只是标记出来。**

### 层级的数据表达

扁平表 + parent 指针（Scratch 模式），已定：

```ts
interface FormalObject {
  parent: ObjId | null    // 所属 subgraph/group

}
interface Group {
  id, kind: 'group' | 'subgraph'

  ports?: Port[]          // 只有 subgraph 有
}
```

**任意深度嵌套天然支持**（这就是你之前担心"md 能不能无限嵌套"的答案：扁平表 + parent 指针可以，md 不行）。

## 一、单件/装配体要分吗——不需要，已经被你自己的架构解决了

**你的直觉是对的，而且原因可以说清楚。**

### 先说 SolidWorks 为什么混乱

不是 SW 团队设计得差，是**历史遗留 + 性能妥协**造成的：

- **零件（Part）**：单一实体的特征历史树（B-rep + 参数化历史），90 年代设计，那时候内存以 MB 计
- **装配体（Assembly）**：因为一个设计放不进内存，被迫拆成多个文件，靠"外部引用"拼起来——**这是内存限制逼出来的补丁，不是概念上必须**
- **草图（Sketch）**：2D 约束求解器，是完全独立的子系统，被塞进零件环境内部

三者是**三套不同的求解器、三套不同的文件格式，靠胶水粘在一起**。你感觉到的混乱，本质是"三个系统的拼接缝"。

### 你的架构为什么天然没有这个问题

你已经定了：**扁平表 + parent 指针 + Group/Subgraph 递归嵌套**。

在这套结构里：
- "零件" = 一个叶子较多、没有子 subgraph 的普通 subgraph
- "装配体" = 一个内部全是 subgraph 的 subgraph
- **它们是同一种数据结构，只是嵌套深度和内容不同**

不需要两套求解器、两套文件格式。**这正是"底层同构而非硬分异构电池"那条决定的自然延伸**——你在架构层面已经避开了 SW 的病根，不用再单独设计"装配体模式"。

唯一需要注意的：**subgraph 的端口契约要能表达"这是个成品黑箱"vs"这是个正在拼接的容器"**，但这只是 `props` 里一个标记位（比如 `sealed: boolean`），不需要另开一套子系统。

## 二、元数据格式（存储层）——这跟架构、内存、开源都有关系，但可以分开决定

你问"是不是跟架构有关系"——**是的，但关系是单向的**：内存架构决定了存储格式**不能**是什么（不能是纯树形的 md），但存储格式本身还有得选。

### 候选方案对比

| 方案 | 可读性 | 性能（大图） | git diff 友好 | 开放性 | 实现成本 |
|---|---|---|---|---|---|
| 单个大 JSON | ✅ 高 | ❌ 差（全量读写） | ⚠️ 中（顺序不稳定会吵） | ✅ 完全开放 | 低 |
| 目录 + 多个小 JSON | ✅ 高 | ⚠️ 中 | ✅ 好 | ✅ 完全开放 | 中 |
| **SQLite 单文件** | ⚠️ 需工具查看 | ✅ 好 | ❌ 差（二进制） | ✅ **规格完全公开，全球最普及的文件格式之一** | 中 |
| 自定义二进制 | ❌ 差 | ✅ 最好 | ❌ 差 | ❌ 除非自己写文档 | 高 |
| Zip 容器（内含 JSON/资源） | ✅ 打开后可读 | ⚠️ 中 | ⚠️ 中 | ✅ 开放 | 中（.docx、.3mf、FreeCAD 的 .FCStd 都这么干） |

### 我的推荐：**SQLite 单文件为主存储，JSON 为导出/调试格式**

理由：

1. **SQLite 不等于"不开放"。** 这是个常见误解。SQLite 的文件格式规格是公开文档（sqlite.org 上有专门一页叫"SQLite as an Application File Format"，就是推荐别人这么干的），任何人拿 DB Browser for SQLite 这种免费工具就能打开看、改。它比"自己发明的二进制格式"开放得多，只是不如纯文本那样"眼睛直接读"。

2. **性能天然匹配你的数据结构。** 你已经定了"扁平表 + ID 引用"——这就是关系数据库的原生形态。`objects` 表、`edges` 表、`blocks` 表，直接对应 SQL 表，索引、外键约束、事务全部免费获得。这些东西你要是用 JSON 自己写，等于重新发明一个残缺版数据库。

3. **真实案例站得住脚**：Fossil（Git 的替代版本控制系统，SQLite 作者自己写的）、很多手机 App 的本地存储、甚至一些 CAD/BIM 工具都直接用 SQLite 当文件格式。**它是"专业但低调"的选择，跟你项目"boring but load-bearing"那部分气质一致。**

4. **配套导出**：做一个"导出为 JSON"和"导出为 md"的功能（前面已经定过），这满足"人类想读"和"给 Obsidian 用"的需求，不需要让主存储承担这个责任。

**如果你现阶段觉得 SQLite 学习成本高**，退而求其次用**目录 + 多个小 JSON 文件**（每个 subgraph 一个文件），性能会差一些，但对高中生阶段的你上手更快，以后性能不够再迁移到 SQLite（迁移成本不高，因为你的内存模型不变，只是序列化层换了实现）。

## 三、软件本体开源吗——这是另一条独立的轴，跟存储格式无关

**文件格式开放 ≠ 软件开源。这是两件完全独立的事，很多人会混。**

举例：
- Adobe 的 PSD 格式规格是公开的，但 Photoshop 不开源
- glTF（3D 模型交换格式）是开放标准，各家实现可以开源可以不开源
- SQLite 数据库文件格式开放，但用它的具体软件想开源就开源，想商用就商用

### 给你的建议：**分层决定，不要一刀切**

| 层 | 建议 | 理由 |
|---|---|---|
| **数据格式规格（schema）** | ✅ 公开文档 | 哪怕软件不开源，格式规格公开能让别人写插件/转换器，生态才能长（对标 ONNX/glTF 的精神） |
| **核心引擎（求值器、图算法）** | 建议开源 | 这是"boring infrastructure"，开源换社区信任和贡献，你自己前面提过想做"基建"，基建这类东西闭源很难被信任 |
| **UI/画板本体** | 可以先不开源 | 商业化空间在这里，如果以后想做成产品，UI 层留一手也合理 |
| **预制块/电池生态** | ✅ 必须开放接口 | 你自己提过"生态是后话"，但接口现在就要设计成对第三方友好，不然生态长不出来 |

**类比**：Blender 是完全开源（软件+格式）；Unreal Engine 是源码可见但商业许可（格式部分开放）；SolidWorks 是完全闭源闭格式。你不需要现在选边站，但**数据格式规格建议现在就往公开方向设计**（哪怕暂时不发布），因为这决定了你的 API 设计习惯——公开的心态会逼你把接口设计得更规范，这对你自己写代码也是好事。

## 四、"跟内存、运行时有什么关系"——讲清楚这三层如何联动

```
┌─────────────────────────┐
│   磁盘：SQLite 文件        │  ← 序列化格式，"关机后留下的东西"
├─────────────────────────┤
│   加载/保存                │  ← 一层薄的映射代码，版本迁移在这里做
├─────────────────────────┤
│   内存：运行时对象图         │  ← 真正跑的时候用的结构，可以跟磁盘格式不同
│   （Node/Edge/Port 对象，   │
│    带缓存、索引、脏标记）    │
├─────────────────────────┤
│   求值器 / tick 循环        │  ← 只跟内存结构打交道，不关心磁盘格式
└─────────────────────────┘
```

**关键原则：磁盘格式和内存结构可以不是同一套东西，中间靠"加载器/保存器"转换。**

这给你一个重要的自由度：**磁盘格式定下来之后，内存结构可以随便优化，不影响存档兼容性**——只要加载器知道怎么把老格式的数据填进新的内存结构就行。

这里最容易被忽略但迟早要还的债是：**版本迁移**。你的 schema 一定会改（加字段、改字段含义），如果不现在就规划版本号，以后老文件全部打不开。

**具体做法（现在就加，成本极低）**：
```sql
CREATE TABLE meta (key TEXT, value TEXT);
INSERT INTO meta VALUES ('schema_version', '1');
```
每次改 schema，version +1，加载时检查版本号，不匹配就跑迁移脚本。Blender 用一套叫 **DNA/RNA** 的机制做这件事（老版本的 `.blend` 文件几十年后依然能被最新 Blender 打开），核心思路就是"存档里带着自己的结构描述，加载器按描述做字段映射"，你不需要做到它那么复杂，但"存版本号 + 写迁移函数"这个最低配现在就该建。

| 问题 | 答案 |
|---|---|
| 单件/装配体要分吗 | 不用，group/subgraph 递归结构已经统一了这个概念 |
| 元数据用什么格式 | **SQLite**（性能好、格式公开、成熟），配 JSON/md 导出给人看 |
| 存储格式开放吗 | 建议 schema 公开文档化，即使暂不开源代码 |
| 软件本体开源吗 | 独立决策，建议核心引擎开源，UI 可以先不开源 |
| 跟内存/运行时的关系 | 磁盘格式只是序列化，内存结构可以不同，中间靠加载器桥接 |

## 二、为什么核心引擎建议用 Python，不是 JS

这是最反直觉但最关键的一个选择，值得展开讲。

### 你的项目有两条腿，一条在 JS 世界，一条在 Python 世界

- **UI/画板交互** —— 这是前端的活，JS/TS 生态（React、Canvas 库）无可替代
- **AI agent（LangGraph）、科学计算电池（numpy/scipy/FEniCS 之类）、未来的预制块生态** —— **这些几乎全部是 Python 生态**，LangGraph 本身就是 Python 库，你想接的科学计算库基本也全是 Python

如果核心引擎用 JS 写，你以后每接一个 Python 库当"电池"，都要过一层子进程调用的桥；如果核心引擎本身就是 Python，"电池"直接 `import` 就行，agent 需要跑 LangGraph 也是原生调用，不隔一层。

**这是用"哪边的活更重"来决定语言，不是随便选。** 你这个项目里，"画布怎么画"是相对成熟、有大量现成库能抄的部分；"图怎么算、agent 怎么跑"才是你真正的核心创新，这部分放在它天然的生态（Python）里，阻力最小。

### 具体架构

```
┌──────────────────────────┐
│ Electron 窗口              │
│  ┌────────────────────┐  │
│  │ React + React Flow  │  │  ← 只管画、只管交互
│  │ (纯前端，无业务逻辑)  │  │
│  └─────────┬──────────┘  │
│            │ WebSocket    │
└────────────┼──────────────┘
             │
┌────────────▼──────────────┐
│ 本地 Python 进程 (FastAPI)  │
│  - 图数据结构 / SQLite      │  ← 真正的引擎，之前设计的一切在这
│  - tick 求值器              │
│  - agent 编排 (LangGraph)   │
│  - "电池"= 直接 import 库    │
└────────────────────────────┘
```

前端发消息"帮我把 A 连到 B"，后端校验、改图、算一 tick、把结果推回来——这跟你之前定的"agent 走 API 不直接碰数据"是同一个模式，UI 本身也走这个 API，agent 和人用同一套接口。

## 三、渲染层：先用现成的，别自己画

**React Flow** 是 MVP 阶段的正确选择——你上手成本最低，社区教程最多，几十行代码能跑起来。

但你之前的规划里提过"几千个死块"的量级，React Flow 默认是 DOM 渲染，节点一多（500+）会掉帧。**这个坑现在知道就行，不用现在解决**——等你做出来发现真的卡了，再把渲染层换成 **PixiJS**（WebGL，ComfyUI 某些同类工具在用）或 **Konva.js**（Canvas 2D），逻辑层不用大改，因为你的数据模型（节点/边的对象）跟渲染库解耦，换皮肤而已。

## 四、为什么是 Electron 不是 Tauri（现阶段）

Tauri（Rust 内核 + 网页前端，比 Electron 包体小很多）现在很火，很多人会推荐它。但对你现阶段：

| | Electron | Tauri |
|---|---|---|
| 学习成本 | 全 JS，教程海量 | 需要碰 Rust（哪怕只是配置） |
| 跟 Python 后端通信 | 直接起子进程/连 WebSocket，无障碍 | 同样可以，但文档/案例少很多 |
| 包体大小 | 大（100MB+） | 小（几 MB） |
| 对你现阶段的影响 | 个人用，包大点无所谓 | 优势用不上，学习成本先扣血 |

**结论：先 Electron，把产品做出来跑起来。** 如果以后要真发布给别人用、在意下载体积，再迁移到 Tauri——因为你的核心逻辑在 Python 后端，前端只是个壳，**迁移壳的成本远低于迁移逻辑的成本**，这是你现在选 Electron 不会被"锁死"的原因。

## 五、分发/打包：具体怎么做

你说"从前面看应该是分发个人软件"——对，目标是**做成一个双击打开的 App**，不是网页服务。

### 打包流程

```
1. Python 后端 → PyInstaller 打成单个可执行文件（.exe / mac可执行）
2. Electron 项目里把这个可执行文件当"资源文件"塞进去
3. Electron 启动时，自动在后台拉起这个 Python 可执行文件（当子进程）
4. electron-builder 打出最终安装包（.exe / .dmg / .AppImage）
```

**关键好处**：最终用户（包括你自己在另一台电脑上）**不需要装 Python、不需要装 Node**，双击安装包就能跑，因为 PyInstaller 已经把 Python 解释器和依赖库全部打进那一个可执行文件里了。

### 跨平台

Electron + PyInstaller 都支持 Windows/Mac/Linux，**但要注意**：PyInstaller 不能"交叉打包"（不能在 Mac 上直接打出 Windows 版），每个平台要在对应系统上（或用 CI，比如 GitHub Actions 跑三套虚拟机）各打一次。个人阶段你大概只需要打你自己电脑那个平台的版本，不用纠结这个。

### 一个诚实的提醒（省得你踩坑）

**PyInstaller 打包这条路是出了名的"看起来简单，细节磨人"**——尤其你以后如果接了 numpy/scipy 之类的大型科学计算库，打包出来的文件会很大（几百 MB 到 1GB+ 不罕见），偶尔会漏打某个隐藏依赖导致"在我电脑上能跑、打包后崩了"。这不是你选错了技术栈，是这条路本身的已知代价，先知道，遇到了别慌，是常见问题，网上大多有解法（`--collect-all` 之类的参数）。

## 六、版本控制/分发的一个连带问题

你的存储是 SQLite（二进制），这意味着：**你自己用 git 管理这个项目的源代码没问题，但用户的"作品文件"（.db）不适合传统 git diff。**

如果你希望"作品"本身也能被版本控制（比如你自己想追溯 MCM 那次调度草稿的历史），前面提过的"导出为 JSON/md"功能这时候就有了第二个用途：**导出即 git 友好快照**，你可以让软件在每次保存时自动生成一份 JSON 副本进一个 `.snapshots/` 文件夹，这份 JSON 才拿去 git 管理，SQLite 文件本身不进 git。

# 二、几种可行的技术路线

## 方案 A：全 TypeScript + Tauri

```text
Tauri
├── 前端：React + TypeScript
├── 图画布：React Flow / 自绘 Canvas / PixiJS
├── 核心图模型：TypeScript
├── 本地存储：SQLite 插件或浏览器数据库
├── Agent：TypeScript 插件
├── 脚本：JavaScript / TypeScript
└── 高性能计算：WASM 或外部插件
```

这是我现在最推荐你认真考虑的方案。

Tauri 的后端是 Rust，前端可以是 React、Vue、Svelte 等 Web 技术；官方架构也明确支持通过插件让 Rust 能力暴露给 JavaScript。Tauri 本身的代码采用 MIT 或 Apache-2.0 许可，但具体插件和依赖仍要单独检查许可证。[citation,tauri.app](f1b896)

### 优点

- 前端图编辑器生态最丰富；
- TypeScript 很适合表达节点、端口、边、命令、事件这些结构；
- 可以先做 Web 版，后面再套 Tauri；
- Tauri 比 Electron 轻，分发包更小；
- 不需要一开始处理 Python 子进程；
- Agent 可以直接成为一个插件；
- 未来可以通过 WASM 接入部分计算能力；
- 适合你说的“本体自己造，Agent 只是插件”。

### 缺点

- 你需要接触一点 Rust；
- Tauri 的一些系统级能力要通过插件；
- SQLite、文件系统、终端、进程管理等能力需要认真设计；
- React Flow 适合 MVP，但大规模自由画布可能需要后面换渲染层。

不过关键是：

> 你不必一开始“学会 Rust 才能开始”。  
> 可以先把 Rust 当成 Tauri 的壳和少量系统桥接层，核心图模型先用 TypeScript 写。

# 四、WASM 在你这里应该扮演什么角色

WASM 不是一种完整的软件架构，而是一种“把其他语言编译成浏览器或沙箱可运行模块”的方式。

可以这样理解：

```text
你的核心程序：TypeScript
用户想接入的计算模块：Rust / C / C++ / Go / Python 的一部分
编译后：WASM
通过统一接口：接入你的节点
```

例如：

```ts
interface ComputePlugin {
  manifest(): PluginManifest
  evaluate(input: ValueMap): Promise<ValueMap>
}
```

WASM 模块只需要实现这个接口。

### WASM 适合：

- 数学计算；
- 图算法；
- 解析器；
- 几何算法；
- 轻量仿真；
- 沙箱执行；
- 不依赖复杂系统资源的纯函数。

### WASM 不适合：

- 任意 Python 库；
- 复杂文件系统操作；
- 启动终端；
- 调用 GPU 驱动；
- 长时间运行的桌面 Agent；
- 依赖大量本地动态库的科学软件。

所以不要想：

> “以后全部都编译成 WASM。”

应该想：

> “WASM 是插件的一种运行方式。”

# 五、Agent 不要成为本体依赖

这一点你判断得很正确。

你的本体应该不依赖 LangGraph，也不依赖某个特定 Agent 框架。

可以设计成：

```text
核心应用
├── Graph Model
├── Command API
├── Event System
├── Persistence
├── Evaluator
└── Plugin Runtime
```

Agent 只是：

```text
Agent Plugin
├── 对话窗口
├── 模型适配器
├── 工具调用器
├── 任务循环
└── Graph API Client
```

Agent 的核心权限应该是：

```ts
interface AgentTools {
  queryGraph(...)
  createObject(...)
  createGroup(...)
  connectPorts(...)
  editMarkdown(...)
  runEvaluation(...)
  inspectErrors(...)
  undo(...)
}
```

而不是：

```ts
agent直接打开数据库文件
agent直接改SQLite
agent直接修改内存对象
agent直接操作UI组件
```

# 六、Agent 协议应该自己定义，还是直接使用 MCP？

可以两层设计。

## 内部协议：你自己定义

例如：

```ts
type Command =
  | { type: 'create_block'; ... }
  | { type: 'promote_block'; ... }
  | { type: 'connect_ports'; ... }
  | { type: 'move_objects'; ... }
  | { type: 'set_property'; ... }
```

这是真正属于你的核心协议。

## 对外适配：以后支持 MCP

MCP 可以作为一个外部适配层：

```text
MCP Client
   ↓
MCP Adapter
   ↓
你的 Graph Command API
   ↓
图模型
```

这样你不需要让 MCP 渗透核心。

MCP 不是你的数据模型，也不应该成为你的内部事务系统。它只是：

> 一种让外部 Agent 发现工具、调用工具的协议。

同理，你也可以以后支持：

- HTTP API；
- WebSocket API；
- CLI；
- MCP；
- 自定义插件 API；
- Python SDK；
- JavaScript SDK。

# 七、你说的“强传染性协议”需要分清两类

你可能混合了两种“传染”。

## 1. 许可证传染

例如：

- GPL；
- AGPL。

Cherry Studio 的 Community Edition 目前采用 AGPL-3.0；Chatbox 的 Community Edition 采用 GPLv3；RikkaHub 公开仓库采用 AGPL-3.0。[citation,github.com](64bcb4) [citation,github.com](15df53) [citation,github.com](5b4151)

这意味着你如果直接复制、链接、修改其中受许可约束的代码，可能产生相应的开源义务。尤其是 AGPL 还关注通过网络提供修改版服务的情形。

## 2. 技术协议传染

例如：

- 你的核心对象必须变成某个框架的状态对象；
- 所有插件都必须继承某个 Agent 基类；
- 所有节点都必须接入某个框架的生命周期；
- 数据格式被某个库绑死。

这个不一定是法律问题，但会造成架构耦合。

你的核心应该避免这两种传染：

```text
核心模型：自己定义
核心命令：自己定义
核心存储：自己定义
核心事件：自己定义
外部框架：适配器
```

# 一、`localhost` 到底是什么

`localhost` 就是“这台电脑自己”，通常等价于：

```text
127.0.0.1
```

当终端显示：

```text
http://localhost:5173
```

意思是：

```text
浏览器
  ↓ 访问
你电脑上正在运行的一个程序
  ↓
它把网页文件发给浏览器
```

这个程序叫“本地开发服务器”。

例如 Vite 项目运行：

```bash
npm run dev
```

实际上启动了 Vite 的开发服务器：

```text
Vite 开发服务器
├── 读取 React/TypeScript 源代码
├── 临时编译和转换
├── 把网页发给浏览器
├── 监听文件变化
└── 修改代码后自动刷新
```

你关掉终端，`localhost:5173` 通常也就访问不了了。

# 二、它有后端吗？

不一定。常见有三种情况。

## 情况 A：纯前端，没有业务后端

很多“一句话 Web 游戏”属于这种：

```text
浏览器
├── Three.js / Canvas 渲染
├── JavaScript 游戏逻辑
├── 键盘鼠标输入
└── localStorage 保存少量数据
```

Vite 虽然启动了一个“server”，但它只是**开发服务器**，不是业务后端。

这类 Minecraft Demo 可能把所有东西都放在浏览器里：

```text
方块世界
人物运动
碰撞检测
简单存档
UI
```

因此 `localhost` 不等于“有后端”。

## 情况 B：前端 + 本地后端

例如：

```text
浏览器 React
      ↓ HTTP / WebSocket
本地 Node.js / Python 服务
      ↓
SQLite / 文件系统
```

这时候可能同时运行：

```text
localhost:5173  → 前端
localhost:8000  → 后端
```

前端负责显示，后端负责：

- 数据库；
- 文件；
- Agent；
- 权限；
- 长时间任务；
- 多人同步。

## 情况 C：前端开发服务器代理远端服务

```text
localhost 页面
      ↓
OpenAI API / 云数据库 / 远程服务器
```

界面在本地，数据或 AI 能力在互联网。

# 三、这是不是“源码分发”？

## 开发阶段：接近，但准确说是“从源码运行”

AI 通常帮你生成：

```text

├── package.json
├── src/
├── public/
├── vite.config.ts

```

你需要执行：

```bash

才能打开。

1. 安装 Node.js；
2. 安装依赖；
3. 运行命令；
4. 浏览器打开 localhost。

这可以叫：

> 从源码运行，而不是面向普通用户的应用分发。

但注意，`localhost` 本身不意味着源码会发给最终用户。它只是当前开发运行方式。

## 发布成网站后：不是源码分发

可以执行：

```bash
npm run build
```

得到：

```text
dist/
├── index.html
├── assets/*.js
└── assets/*.css
```

然后部署到：

- GitHub Pages；
- Cloudflare Pages；
- Vercel；
- 自己的服务器。

用户直接访问网址，不需要 Node.js，也不需要拿到你的 TypeScript 原始源码。

不过浏览器必须下载编译后的 JavaScript，所以它不像原生二进制那样难以查看。严格说这是“前端产物分发”，不是“原始源码分发”。

## 打包成桌面应用后：是普通应用分发

相同的 React 页面可以塞进：

- Electron；
- Tauri。

最后生成：

```text
Windows: .exe / .msi
macOS:   .app / .dmg
Linux:  .AppImage / .deb
```

用户双击打开，不会看到 `localhost`，也不需要安装 Node.js。

内部仍然可能使用 Web 技术，但对用户而言它就是桌面应用。VS Code、Discord、Obsidian、部分 AI 客户端都属于类似思路。

# 四、为什么 Vibe coding 都喜欢先生成 localhost Web 项目

因为这是目前 AI 最容易生成成功的形式。

## 1. Web 技术的训练数据最多

AI 看过大量：

- HTML；
- CSS；
- JavaScript；
- React；
- Vite；
- Three.js；
- Canvas；
- 开源 Web 项目。

所以生成速度最快。

## 2. 反馈循环短

修改代码后，浏览器立刻刷新：

```text
描述需求
→ AI 改代码
→ 浏览器刷新
→ 看结果
→ 再描述
```

不需要每次重新编译和安装桌面应用。

## 3. 不用先解决打包问题

桌面打包会立即引入：

- Windows 签名；
- macOS 公证；
- 安装器；
- 系统权限；
- 自动更新；
- 多平台构建；
- 原生依赖。

这些都跟“核心想法是否可用”无关，所以原型阶段通常先避开。

## 4. 浏览器已经提供了完整运行时

浏览器免费提供：

- 文字和图形渲染；
- Canvas / WebGL；
- 音频；
- 鼠标键盘；
- 网络；
- Worker；
- 本地存储；
- 调试工具。

因此 AI 不需要从窗口系统开始造。

- 高效网格合并；
- 大规模存档；
- 光照传播；
- 多人同步；
- 完整物品系统；
- 稳定碰撞；
- 性能退化；
- 崩溃恢复；
- 输入异常；
- 版本迁移；
- 长期维护；

> 一句话生成的是“可交互的概念证明”，不是经过工程化的产品。

- 撤销/重做永远正确。

而你的项目恰恰更依赖后面这些“不容易展示但决定生死”的部分。

7. 保存并重新加载；
8. 执行撤销和重做。

如果这一套不好用，打包成 `.exe` 也没有意义。

## 2. 第一版可以完全没有业务后端

你可以先把它做成纯前端：

```text

   ↓

   ↓

```

所有东西都在浏览器中运行：

- 图模型；
- Markdown；
- 命令系统；

- 本地存储；

这能大幅降低复杂度。

之后才把持久化替换成：

```text
Tauri
  ↓

```

```ts

  load(id: string): Promise<Project>

```

```

```ts

```

核心图模型不用改。

## 3. Agent 第一版也不需要业务后端

如果调用云端模型 API，可以由浏览器发请求，但存在 API Key 暴露和跨域等问题。个人原型阶段可以临时这么做，正式版再移入桌面端安全层。

不要一上来做完整对话、记忆、MCP、多模型、知识库。那会让 Agent 界面盖过你的真正创新。

## 二、AI agent 家族：最有参考价值的一组

### opencode —— 你该抄的那个架构

活跃项目是 anomalyco/opencode（SST 团队做的），MIT 许可。它的核心设计就是**客户端-服务器**：一个用 TypeScript 写、跑在 Bun 上的本地 HTTP 服务器负责模型调用、工具执行、状态管理，并公开 OpenAPI 3.1 规范和官方 SDK，所以终端 TUI、桌面版、IDE 插件都只是连接同一个服务器的不同客户端 [citation,datacamp.com](59127f) [citation,nimbalyst.com](168906)。注意还有一个 2025 年 9 月停更的 Go 版 opencode-ai/opencode，别装错 [citation,datacamp.com](59127f)。

**对你的意义**：这正是我前面给你画的“graph-core + 本地 API + UI/Agent/CLI 都是客户端”结构的现成证明。它甚至证明“终端、桌面、IDE 可以共享一个引擎”这条路是通的。

### Claude Code —— 闭源但“半透明”

Anthropic 官方 CLI，**闭源**，但通过 npm 分发，所以代码是混淆但可读的 JS。单进程 Node 应用，不拆前后端——和 opencode 形成鲜明对照：**闭源厂商倾向单进程黑盒，开源项目倾向 API 化**（因为 API 化是生态招募手段）。

### Codex —— 打包教训的活教材

Apache-2.0 开源。最初 TypeScript 写的，后来官方用 Rust 重写，理由非常直白：**零依赖安装**——很多用户没有 Node 22+，这是分发障碍 [citation,devclass.com](62ae45)。现在 Rust 占代码约 95%，单个自包含二进制，npm/brew/直接下载三种装法 [citation,augmentcode.com](0fe7a3) [citation,devclass.com](62ae45)。连 Simon Willison 都利用它 Apache 协议 + Rust 源码可读的特性去改造它访问内部 API [citation,simonwillison.net](d97002)。

**对你的意义**：这是“TS 原型 → 成熟后可选重写成单二进制”路径的官方示范。你第一阶段用 TS 完全没问题，分发痛点出现时再考虑。

### OpenClaw —— 和你哲学最像的一个

Peter Steinberger（PSPDFKit 创始人）做的个人 AI 助理，MIT，TypeScript 写的约百万行代码，347k stars。经历 Clawdbot→Moltbot→OpenClaw 三次改名（Anthropic 商标投诉）[citation,wikipedia.org](5260d9)。

架构上最有意思的是三点：

1. **单端口 WebSocket Gateway**：50+ 个消息渠道（WhatsApp/Telegram/Discord…）不两两对接，全部汇入一个本地常驻网关（默认 localhost:18789），把 N×M 的对接问题降为 N+M [citation,geekyants.com](86399e) [citation,medium.com](c04fce)
2. **个性化全靠工作区 md 文件**：SOUL.md（人格）、AGENTS.md（规则）、MEMORY.md（记忆），改文件即改行为，可逆且免微调 [citation,skywork.ai](2dfe30)
3. **技能就是 markdown**：ClawHub 上上万个社区技能都是 md 文档描述的，配合 cron/心跳的常驻 agent 层 [citation,medium.com](c04fce)

**对你的意义**：这直接验证了你前面纠结的“md 当输入层、结构层在下面”的分层——OpenClaw 把“agent 的人格、规则、记忆、技能”全部 md 化作为**编辑界面**，底下是结构化的 Gateway。这就是“md 是输入法不是文件系统”的百万行级实践。另外它的“单网关 + 多渠道”就是你“单图引擎 + 多客户端”的同构。

## 三、Obsidian：闭源软件 + 开放格式的生存样本

- **本体闭源**，Electron 壳（所以它才能一个代码基吃 Windows/Mac/Linux/手机）
- **格式全开放**：保险库就是一个普通文件夹，笔记是纯 .md，画布是 .canvas（JSON），配置是 .json
- **插件是 JS**：运行在 Electron 渲染进程里，能拿到一定的 Node 能力，社区插件几千个，是它真正的护城河
- 商业模式：软件免费，卖同步/发布服务

**对你的意义**：这是“**代码闭源没关系，格式开放就够了**”的最好证据。用户信任来自“我的数据随时能走”，不来自“你的源码我看过了”。你之前问“要不要开源”——Obsidian 路线（格式公开文档化 + 本体随便）是成立的，尤其你说过你的差异化在核心机制而不在生态。

## 四、科学计算三件套：老牌架构的教训

### Orange —— 最接近“你的同类”

GPL-3.0+（因为 GUI 建立在 Qt 上，Qt 的 GPL 选项导致整体传染）[citation,orangedatamining.com](998b5b)。技术栈是 Python + Cython + C++，GUI 是 PyQt [citation,wikipedia.org](d379b2)。

三个值得抄的点：

1. **代码库刻意拆成三块**：`orange-canvas-core`（画布引擎）、`orange-widget-base`（widget 基类库）、`orange3`（本体+全部 widget）[citation,pypi.org](ffa5f8) —— 这就是你该做的 graph-core / graph-commands / app 的分拆
2. **扩展就是 pip 包**：add-on 装进 conda 环境即自动出现在画布上，没有独立插件市场 [citation,pypi.org](ffa5f8)
3. **调度**：它有自己的 scheme 执行引擎——widget 之间信号槽驱动、可分线程执行，是“数据流图怎么调度”的学术级答案

一个反面教训：**它的工作流文件 .ows 历史上用 Python pickle 序列化**——pickle 把对象结构直接固化，跨版本迁移和安全性都很差。这就是你前面定“自定义 schema + 版本号 + JSON/SQLite”时躲开的坑。

### Octave / CPython —— “内核+解释器”的经典配方

- **Octave**：GPL。C++ 写的解释器和 liboctave 数值库（BLAS/LAPACK 底座），.m 语言兼容 MATLAB，GUI 用 Qt 但可选，核心是 CLI。调度就是解释器主循环，重计算交给底层多线程库。
- **CPython**：PSF 许可（宽松、GPL 兼容）。C 内核 + C API，生态靠“编译型二进制 wheel + ABI 标签”分发，GIL 决定了它的并发模型。

这两个加上 Blender，共同示范了一个配方：

> **重内核用 C/C++，用户可编程层用解释器（Python/.m），扩展靠原生二进制包分发。**

你注意到的现象在这里得到解释：**为什么科学计算工具全是 Python 生态**——因为 CPython 的 C API 让“内核作者”和“脚本作者”可以分层共存三十年。

### Blender —— 和你气场最合的老前辈

- **GPL-2.0+**，整体传染，靠 Blender 基金会+发展基金养活，证明了 GPL 不会杀死生态，反而防止了闭源分叉
- **不用 Electron 也不用 Qt**：自绘整套 UI（OpenGL/Vulkan/Metal 抽象层），代价是工程量巨大，收益是完全自主的性能和控制
- **内嵌 CPython**：插件全是 Python，且 Python 许可与 GPL 兼容
- **.blend 格式的 DNA 机制**：二进制文件里自带结构描述（字段名、类型、偏移），所以几十年前的 .blend 今天还能打开——这就是我前面让你存 `schema_version` 的祖宗级实现
- **调度**：依赖图（depsgraph）做脏传播——改一个参数，只把受影响的下游标记为 dirty 重算。**这就是你 tick 求值器要做的“status 传播”的工业级版本**，Blender 的源码值得你以后读这一部分

## 五、横向规律总结（这才是对你有用的部分）

### 规律 1：所有 agent 工具都没有“内核”

opencode/Claude Code/Codex/OpenClaw 四个加起来，本体全是**编排壳**——智能在远端 API，计算在用户文件系统里执行。你的项目正好相反：**你要有内核（图模型+求值器），agent 只是客户端之一**。所以这四家给你的是“客户端协议、MCP、沙箱、会话管理”的参考，不是架构模板。

### 规律 2：许可证光谱清晰对应商业模式

| 许可 | 代表 | 效果 |
|---|---|---|
| MIT/Apache（宽松） | opencode、Codex、OpenClaw | 新生开源项目的标准选择，无传染，你借鉴代码/思路都干净 |
| GPL（传染） | Blender、Orange、Octave | 靠"防闭源分叉"保护共同体，Orange 的 Qt 选择是典型被动传染 |
| 闭源+开放格式 | Claude Code、Obsidian | 厂商控制体验，用户靠格式自由离开 |

你之前担心的 AGPL（Cherry Studio 那类）在桌面软件语境下其实约束的是“改了它的代码再分发/提供服务”的场景，**借鉴思路、自己重写**完全不受任何许可证约束——版权保护表达，不保护想法。

### 规律 3：分发方式和技术栈强绑定

- 解释型：走包管理器，**要求用户已有运行时**（这是 Codex 逃离 Node 的原因）
- 编译型：单二进制零依赖
- Electron：安装包大但跨平台一致
- **对你的建议不变**：个人阶段"npm run dev + localhost"就是正确形态，opencode/OpenClaw 的核心用户全是这样跑的

### 规律 4：md 作为“agent 可读写的人格/规则层”已被验证

OpenClaw 的 SOUL.md/MEMORY.md、四家全都支持的 AGENTS.md/CLAUDE.md——**“用 md 描述意图，机器读取结构化执行”已经是这个领域的事实标准**。你的“死块→抓取→正式对象”是它的超集（你还要空间布局和连线），方向没有孤立风险。

### 规律 5：你最该精读源码的三家

按对你项目的信息密度排序：

1. **Orange**（Python，可读性好）——看 `orange-canvas-core` 怎么实现画布/连线/widget 执行调度，几乎就是你的同类项目
2. **opencode**（TS）——看客户端-服务器拆分、命令 API、会话持久化怎么组织
3. **Blender**（只读两块）——depsgraph 的脏传播、.blend 的 DNA 版本化机制

Obsidian 闭源读不了，但它的 `.obsidian/` 配置文件夹和 `.canvas` JSON 格式可以拆开研究——canvas 的 JSON schema 就是“扁平节点表+边表”的一个现成样例。

## 一、先讲原理：签名检查到底在什么时候发生

Windows SmartScreen 和 macOS Gatekeeper 的检查**不是“这个 exe 存在就检查”**，它由两个条件触发：

**条件 1：文件带着“来源标记”**
- Windows：Mark of the Web（Zone.Identifier），**由浏览器、Outlook 等下载工具写入**
- macOS：quarantine 隔离属性，**同样主要由浏览器写入**
- **npm / pip / git / curl 下载的文件，默认不带这两个标记**

**条件 2：通过“双击/图形界面”启动**
- Explorer 双击、Finder 打开 → 检查
- 终端里由某个进程拉起（npm script、npx）→ 不走这条检查链

把两个条件合起来看：

```text
路径 A（会弹窗）：浏览器下载 .exe → 带标记 → 用户双击 → SmartScreen/Gatekeeper 拦截
路径 B（不弹窗）：npm 下载到 node_modules → 无标记 → npx 在终端拉起 → 检查不触发
```

## 二、各通道的真实情况（有差异，注意 brew）

| 通道 | 获取方式带标记吗 | 结论 |
|---|---|---|
| **npm / npx** | ❌ 不带 | ✅ 完全干净，无弹窗，免签名 |

## 四、诚实的代价清单（免签不是零代价）

1. **macOS 自动更新基本无缘**：Electron 的 Squirrel.Mac 和 Tauri 的更新器在 macOS 上要求签名+公证的更新包才能校验通过。所以无签名阶段，你的“自动更新”降级为“打开时检查新版本 → 提示用户去 Releases 重新下载”。个人软件阶段完全够用。

## 二、解耦干净吗——诚实版：有五条缝会漏

绝大多数代码天然干净（因为 React 应用本来就不关心自己跑在哪个 WebView 里），但**有五条缝，浏览器和桌面在这里能力不同**，必须现在用接口封住，否则以后换壳要大改：

| 缝 | 浏览器能做的 | 桌面能做的 | 封法 |
|---|---|---|---|
| 1. **文件系统** | 几乎不能（只能下载/上传） | 完整读写任意路径 | `HostBridge.fs.*` 接口 |
| 2. **存储** | IndexedDB | SQLite | `ProjectRepository` 接口（之前已定） |
| 3. **进程** | ❌ 不能起子进程（python 电池全废） | ✅ 随便起 | `HostBridge.exec()` |
| 4. **网络** | 受 CORS 限制，API key 暴露在 DevTools | 无 CORS，key 存后端 | 模型调用走 `HostBridge.llm()` |
| 5. **窗口件** | 无系统菜单/全局快捷键/多窗口 | 有 | 先不碰，需要时再加接口 |

**关键纪律只有一条**：你的代码里不许出现 `if (isDesktop)` 散落各处。所有平台差异收敛到**一个** `HostBridge` 模块，查询能力而不是判断环境：

```ts
// ❌ 错误
if (window.__TAURI__) { ... } else { ... }

// ✅ 正确
if (host.capabilities.has('fs')) {
  await host.fs.writeFile(path, data)
} else {
  await host.fs.exportFile(data)   // 浏览器降级为下载
}
```

这样解耦就是干净的——**干净的标志不是“没有差异”，而是“差异被关在一个笼子里”**。五条缝里，你现在只需要预留接口名（空实现+浏览器降级版），不用实现桌面版。

顺带：这条纪律对 vibe coding 极其重要，必须写进你的 AI 规则文件里（AGENTS.md），否则 AI 一定会在某个组件里直接调 Tauri API，把缝撕开。

## 一、先承认：你现在乱，是因为把四件不同的事叫成了同一个“抓”

你列的场景其实是**四种操作**：

| 你的动作 | 你在问的 | 真正该叫什么 |
|---|---|---|
| 框选散落文字，按位置猜输入/输出，吸附成一个带口的盒子 | 空间语法 → 封装 | **promote-to-block**（打组/封装） |
| 在一段字里点中 `Q` 或 `3.5`，声明它是变量 | 给内容起类型契约 | **promote-to-var**（声明变量） |
| 已经正式的块上再接线、改端口 | 图操作 | **connect / bind-port** |
| 从面板拖一个预制电池进来 | 跳过草稿 | **insert-prefab** |

**“抓块”不是一种原语，是几种原语的口语混称。**  
哲学一旦混，后端就会跟着混：变量变成块、块变成端口、边变成全局变量。

**统一退阶（建议你立刻采用）：**

```text
内容层永远是 Block（一块可编辑 md，可多开，像便利贴）
语义层永远是 Object（kind 开放：var / process / group / …）
端口是 Object 上的契约，不是独立“东西”
边是一等公民（有 id/type/props/status/delay），但不是变量
```

**正式 ≠ 块。正式 = 语义层里有一条记录。**

- 正式变量：`kind: 'var'` 的 Object，引用某段文本（或没有文本，纯手填）
- 正式块/电池：`kind: 'process' | 'group'` 的 Object，**绑定一组正式变量当端口**，可选注释文本
- 非正式：只有 Block，没有 Object

这样三个问题立刻有答案：

1. **“只抓一列数字当向量”** → 这是 **tovar**（一个 var，dtype=vector），**不是**一个电池块。除非你同时给它套了输入输出契约，才是 process。
2. **“框一堆散字，里面有我想当变量的”** → 先 tovar 那些 token，再 **promote-to-block** 把已声明的 var **绑成端口**。两步，不要一步魔法。
3. **“框一堆完全没有变量的字”** → 只是 **group 注释便利贴**（视觉组），或拒绝 promote，提示“先声明至少一个端口/变量”。不要假装它能跑。

**不要“为什么不鼠标指过去就直接转正式变量”**：预选（hover token）是**候选**，回车才是**声明**。直接转会把错选、单位、注释全变成图节点，图会脏死。

## 二、正式块 vs 正式变量：不要做成同一个东西

你后半段自己已经摸到正确答案：

> 正式块 = 若干正式变量绑在一起的、可带注释的组，建议自带可正可负的存量缓冲

这句话里有两个该保留、一个该改名：

**保留：** 块是**绑定关系**（哪些 var 是这个过程的 in/out/state），不是“一块更大的 md”。  
**改名：** 别叫“块=组=变量数组”。否则嵌套变量、嵌套块、端口会再次串台。

建议对象种类只保留这几档（正交）：

```text
Block          文本便利贴（可多个，哲学就是黑板碎片，不要合并成一个大 md）
Var            有类型/单位/值/status 的量（允许嵌套：record / vector / stream）
Process        有端口契约 + 可选 eval 的电池
Group          纯视觉组合，不参与求值
Subgraph       有对外端口的封装，求值可见
Edge           端口到端口的一等连接（可 delay、可挂 props）
Buffer/Stock   Process 或 Subgraph 上的可选存量（你说的正负缓冲）——是 Var 的一种角色，不是新物种
```

**变量嵌套 ≠ 块嵌套。**

- 流股多维（Aspen）：**一个 Var，dtype = record/stream**，`{T, P, F, x[]}`，**一根边传一整个记录**。禁止“温度一根线、压力一根线”当默认。
- 需要拆字段时：边上或下游用 **field 选择器**（Orange 的 channel 映射），不是平行边森林。
- 块嵌套：只有 Group/Subgraph 的 parent 指针。Var 嵌套走类型系统（record 字段），**不要**让 Var 的 parent 表示“几何上在哪个盒子里”——几何归属是 Block/Group 的事。

**边是不是一等公民？**  
数据结构上：**是**（id、属性、delay、status）。  
语义上：**边不是变量，也不是全局注册表。**  
“注册全局变量”是另一条通道（命名查找），和边正交。默认仍是**显式连线**；全局名是可选的 `alias`，否则图不可读。

## 三、多开文本框：后端不要合成一个

哲学：电脑上的“手写黑板”= **空间上的多张便利贴**，不是一篇 Word。

后端：

- 每个文本框 = 一个 `Block`，有自己的 id 和 rect
- **不要**为了“好存”合并成一个大 md
- 跨框框选 = 多 Block 上的多个 range + 一次命令里批量 tovar / 一次 promote-to-block

“算不算同一个文本框”：**永远不算。** 同一只是用户视觉上靠近，靠近用吸附/对齐处理，不用改数据模型。

## 四、GUI 位置语法会不会绑死后端——会，除非你把“猜测”关在命令参数里

你的担心完全对：若后端按像素猜“左边是输入”，就会变成 SolidWorks 绑 Windows GDI 那种脆。

**解耦法则：**

```text
前端：几何 → 猜一个 Intent（left=in, right=out, 吸附、对齐）
     → 生成一条 Command（带明确的 ports[] / vars[] / layout）
后端：只执行 Command，绝不读坐标、不读缩放、不读 DPI
```

后端健康自测（你要求 agent 必须先有这个）：

1. 零 GUI：纯 API 插入 prefab、声明 var、connect、跑 tick
2. 同一套图用 JSON 加载，坐标全改成乱的，**求值结果不变**
3. 手机/小窗：位置猜测可以更蠢，用户改 chip 确认即可；后端无感

**预制块硬接线**和**黑板抓取**是两条入口，汇合到同一 Command API。  
抓取是创意功能；insert-prefab 是 Orange/GH 工作模式。两条都要，**后端只认第二条的形状（结构化命令）**。

Onshape 能在网页里准，是因为约束求解在模型里（尺寸、重合），不靠像素。你以后若要“准”，加的是**约束/吸附作为生成 Command 的辅助**，不是把像素写进 schema。

## 一、第一天：没有流股，只是更顺手的 draw.io

### 用户是谁（画像很窄，别假装全民）

不是“所有要画图的人”。是三类重叠的人：

**完备的 draw.io 人性化，到此就够了。**

- 复制一坨，线不断、字不丢。

## 二、第二天：抽象概念上出现“有向有权流股”

不要从 GUI 语法引入。从用户已经在做的事**加一层可读的意义**。

### 什么时候我们说“它现在有流了”

当且仅当同时满足：

1. **方向是真的**：A→B 和 B→A 不是同一条线的两种画法，反向是另一条关系（或明确的双向）。
2. **线上可以挂一个值**（权）：数字、短标签、或以后的 record。空着也行，空 = 权未填。
3. **这个值可以沿方向被“读到”**：哪怕第一版只是“点 B 能看见上游写了什么”，人不用把线当装饰脑补。

**还没有流的：** 仅装饰箭头、仅“因为所以”的语文线、仅视觉粗细。  
**已经有流的最小完备：**  
`有向边 + 边上的一份载荷（可空）+ 下游能读到这份载荷`。

不必有仿真、tick、单位、类型。**“有流”= 关系从句子变成了可指向的量。**  
用户感知的一句话：

> “我点这个框，能看见谁流进来、上面写了啥；我改线上的数，对面能显示出来。”

这就够宣布：draw.io 长出了流。

### 有了流之后用户会怎么做（观察，不是规定）

他们**不会**先设计端口表。他们会：

1. 继续当 draw.io 用，偶尔给某几条线写上数字或“3人”“高温”。
2. 发现“改这边，那边字没变”——开始抱怨，这时才需要**传播**（仍可以极简：改边标签 → 下游文本里的引用更新）。
3. 平行线画烦了，自己把几条线捏成一条，线上写 `T,P,F`——这就是 record 流股的**用户发明**，软件事后承认即可。
4. 画出环（心情→效率→心情）。**允许成环。** 第一天“有流”甚至可以不跑环，只显示“这里有环，权是上一笔写下的数”。手册写：要真反馈去开“步进”。不要用禁环当引导。

不当操作空间交给手册：一百根平行线、一个框上五十条出入。像没人拦你在一个零件里画宇宙。软件提供**折叠/一根复合线**当糖，不强制。

## 三、第三天：魔杖——乱画之后框一下，或粉笔能跑

这是用户真正的许愿，拆成他们**手上会做的事**，不是我们的对象模型。

### 许愿 A：“先乱画，框一下变成电池”

用户心理模型是便利贴魔法，不是 CAD 特征树：

1. 黑板上已经有几坨字、几根箭。
2. 框住一坨，说“这是一件事”。
3. **期望立刻看到：** 一个盒子、原来的字还在当注释、箭在盒子边变成“进出的口”（口可以先没名字）。
4. **不期望：** 先声明变量、先选 kind、先对齐网格。错了就拆盒，字回摊上。

“电池”在用户嘴里 = **有进出的一坨**，不是求解器单元。  
完备到此：盒 + 边界上的进/出（来自穿过框的箭）+ 仍可当纸编辑。  
还没有 eval，也可以叫电池——**能接线的注释盒**。

### 许愿 B：“点一下就开始跑，别让我在脑子里补层级和流”

用户要的是**看见动**，哪怕蠢：

- 我给入边写了 `3`，出边或盒上出现 `3` 或 `未算`。
- 我按空格/步进，环上的数挪一格。
- 某条线没写数：下游写“空”，图其余部分照样动。

他们**不会**许愿工业求解器。他们会许：

- 别让我先定义才能画。
- 别让半成品不能看。
- 错了像擦粉笔，不要报错对话框锁死。
- 某一坨我想“就当计算器”时，再教我公式；其余永远是纸。

预制块（Orange/GH）是**另一天的许愿**：“我今天不想发明轮子，给我一个现成盒子丢上去接线。”  
和魔杖不冲突：一个从纸长出盒，一个从库扔下盒。用户两天都会用，看心情。

## 四、操作语法 vs 手册：你发现的那件事是对的

用语法逼人“正确建图”，终点就是古板求解器：每一步合法，但不敢乱画。

更接近黑板的约束层次：

| 层 | 软件做什么 | 例子 |
|---|---|---|
| 物理上不能不做的 | 很少 | 边必须有两个端（或明确悬空）；文件能存开 |
| 默认善良 | 猜，可改 | 框选变组；穿过框的箭变成口 |
| 手册/文化 | 不禁止 | 别把整学期画一张图；别五十根平行线 |
| 可选严谨 | 开关 | 类型检查、单位、步进仿真 |

**引导用默认和糖，不用锁。** SW 一个草图画整机能打开——你的图一张纸画宇宙也必须能打开。

## 一、完备性对标什么（能力清单，不是 UX）

对标 Grasshopper / Simulink / Orange / Aspen 草稿层，**最小完备**是这些能力都存在、且都能只通过 API 做出来（GUI 只是其中一种客户端）：

| 能力 | GH / Simulink 里对应什么 | 你的后端必须有 |
|---|---|---|
| 有向图 | 线、信号线 | Node + Port + Edge |
| 边上有载荷 | 数据树 / 信号 | Edge 传一个 Value（可为 record） |
| 复合载荷 | 一项里很多通道 | `dtype: record \| stream \| vector`，**一根线** |
| 成环 + 时间 | Unit Delay、反馈 | `edge.delay` + 全局 tick |
| 手填打断依赖 | 冻结、Constant | `status: manual` |
| 残缺仍能部分跑 | 部分失效变橙/红 | `undefined` 传染，不整图锁死 |
| 封装复用 | Cluster / Subsystem | Subgraph + 对外端口 |
| 纯视觉整理 | Group（不影响算） | Group，求值不可见 |
| 嵌套类型 | 树/总线 | Var 的类型嵌套，不是几何嵌套 |
| 插件电池 | 组件库 | `kind` + `eval` 契约，insert-prefab |
| 外部计算 | GhPython / S-Function | 以后 `eval: python`，现可不实现 |
| 历史/过程 | 示波器、数据记录 | tick 环形缓冲（可后做） |

**刻意不对标的：** 工业求解器的收敛、网格、单位制执法、形式化验证、必须先定义再连线。  
完备 = **这些动词都有**；严谨 = 用户自己造电池或手册约束。

Agent 建“流仿真 / 对话树”走的就是上表全部动词，**零像素**。

## 二、四个东西，禁止再混名

| 名字 | 是什么 | 嵌套？ | 有没有 GUI 也能存在 |
|---|---|---|---|
| **Block** | 一块 md 便利贴（内容层）。散的未定义文本框 = **只有 Block** | 空间上多开，**数据上永不合并**；不形成求值树 | 能。Agent 可 `createBlock(text)`，也可完全不创建 Block |
| **Var** | 一个有契约的量：名、类型、值、status | **类型可嵌套**（record 里再 record）；**不是**盒子套盒子 | 能。`createVar({name, dtype, value})` 可不绑文本 |
| **Process** | 电池：端口 = 绑上去的 Var + 可选 eval | 不“套 Var”；Var 是端口引用 | 能。`createProcess({ports, eval})` |
| **Group / Subgraph** | Group=视觉盒；Subgraph=有对外口的真封装 | **只有这两种允许几何/结构嵌套** | 能。纯 id + parent |

**正式 = 语义层有 Object（Var 或 Process 或 Subgraph）。**  
Block 永远可以非正式。  
**块 ≠ 变量。** Process 绑定 Var；Var 不是 Process。

散的未定义文本框在干什么？  
**只做人的外置记忆。** 不进求值。Agent 头脑风暴若只需要图，可以一个 Block 都没有。

## 三、“抓块”怎样才不重复不乱

**抓不是后端原语。** 后端只有：

```text
createBlock / editBlock
createVar   （可选 bind 到 Block 的一段 anchor）
bindPort    （Var → Process 的 in/out/stock）
createProcess
createGroup / createSubgraph
connect
```

前端“抓”是**手势宏**，展开成上面几条命令。宏可以笨，命令必须干净。

### 三种手势 → 固定展开（禁止一个万能抓）

1. **tovar**（点 token / 框数字 / 多选）  
   → 只 `createVar` + anchor。  
   **不**创建 Process。一列数字 = 一个 `dtype: vector` 的 Var。

2. **promote-process**（框一坨已经有箭或已有 Var）  
   → `createProcess` + 把穿过框的边收成端口 + 把框内已有 Var bind 到端口。  
   框内纯注释 Block 仍是注释，不自动变 Var。

3. **insert-prefab**  
   → 直接 Process + 端口，无 Block。Agent 默认走这条。

**禁止：** 一次手势既发明 Var 又发明 Process 又重排 md。  
要两下就两下。乱来的空间用手册说“先标量再装箱”，不要用锁。

嵌套规则一句话：

- **值**可以深嵌（流股 record）  
- **图结构**只有 Subgraph/Group 嵌套  
- **Var 不嵌套 Process，Process 不嵌套成 Var**  
- Block 不嵌套 Block（只有空间叠放）

## 四、后端如何自己健康（给 Agent、给以后的 GUI）

自检标准——**没有浏览器也能跑通：**

```text
createVar T, k
createProcess heat, ports {T,k} → q
connect …
set manual T=300
tick × N
assert q 有值或 undefined，图不崩
```

对话树同理：节点是 Process（或 kind=`utterance`），边是有向有权（权重=分支条件，可先当字符串），tick 或显式“走一步”。

GUI 位置猜输入输出 = **只写在 Command.layout / Command.guess 里**，求值器、存储、status **禁止读坐标**。  
这样：前端再 CAD 化，后端仍是工业求解器那张能力表上的一台图机。

## 五、和“先人性 draw.io”怎么并存

不矛盾，是**两层产品、一层内核**：

```text
内核（现在就要健康）：上表全部动词的 API + 存储 + tick
客户端 A：人的纸（可以暂时只用 Block + 无端口的箭）
客户端 B：魔杖（手势 → 命令）
客户端 C：Agent / 脚本（直接命令，insert-prefab）
```

完备性在内核；人性在客户端 A/B。  
工业求解器的“想要什么自己造”= 新 `kind` + 新 `eval`，不改内核。

散文本是纸；Var 是量；Process 是可跑的盒；抓是前端宏。  
对标 GH/Simulink 的是**内核动词齐**，不是抓的手感像它们。  
Agent 只打内核；GUI 不准把像素写进内核——解耦是否干净，用“无界面跑通 tick”一票否决。

# 从四个场景反推：后端到底需要几种东西

先给结论，再逐个场景验证。你现在被前端牵制，是因为**"正式/非正式"被当成了对象类型**——它其实是**每个对象各自的一个状态位**。这个视角一换，你那些"框是不是块""变量要不要单独定""抓的是块还是变量"的纠结会同时消失。

## 一、核心判断：正式性是状态，不是种类

```
❌ 现在的心智模型：
   非正式文本框 ──"抓"──> 正式块（两种不同的东西）

✅ 正确的心智模型：
   每个对象都有 formal: false | true
   "抓" = 把 formal 从 false 翻成 true（并补上契约）
```

为什么必须这样：

- 场景 1 你要"随手画的箭头"和"正式定义的边"共存 → **边也需要 formal 位**
- 场景 4 你说 agent 直接建正式的 → 那它建的是**同一种对象**，只是出生时 `formal: true`
- 场景 1 你说"变量已经在文本里但只是字符" → 那 Var 也有个"还不正式"的阶段

**所以：种类是名词（Node/Edge/Port/Var...），正式性是形容词，正交。**

这一刀切下去，你的对象清单立刻收敛。

## 二、后端最小对象集（我认为可以今天敲定）

```ts
// ============ 唯一真相：五种实体 + 三种关系 ============

// 1. Cell —— 画布上一切"有位置的东西"的基类
interface Cell {
  id: CellId
  kind: 'text' | 'frame' | 'node' | 'var' | 'edge'
  formal: boolean              // ← 关键：正式性是状态位
  rect?: Rect                  // 有位置的才有（edge 没有）
  parent: CellId | null        // 空间归属（见下）
  props: Record<string, any>
}

// 2. 文本单元 —— 你的"自由文本框"
interface TextCell extends Cell {
  kind: 'text'
  text: string                 // md 源文本
  // formal: false → 就是黑板上的一坨字
  // formal: true  → 它成为某个节点的注释体/文档
}

// 3. 框 —— 你纠结的那个东西
interface FrameCell extends Cell {
  kind: 'frame'
  // formal: false → 纯视觉圈（draw.io 的容器）
  // formal: true  → Subgraph，有命名空间和对外端口
  ports?: Port[]               // 只有 formal 才有
  namespace?: string           // 框名.局部变量名
}

// 4. 节点 —— 电池/过程
interface NodeCell extends Cell {
  kind: 'node'
  ports: Port[]                // formal:false 时可以是空数组
  eval?: EvalSpec              // 怎么算，可选
}

// 5. 变量 —— 有契约的量
interface VarCell extends Cell {
  kind: 'var'
  name: string
  dtype: DType                 // 递归类型，见下
  value?: any
  status: Status
  scope: CellId | 'global'     // ← 回答你的"变量定义在哪"
  anchor?: Anchor              // 可选：绑到某段文本
}

// 6. 边 —— 一等公民
interface EdgeCell extends Cell {
  kind: 'edge'
  from: PortRef | CellId       // formal:false 时可以只指向 Cell（悬空箭头）
  to: PortRef | CellId | null  // null = 悬空，合法
  delay: boolean
  payload?: DType              // 载荷类型
  props: Record<string, any>   // 权、标签、颜色
}
```

**就五种。** `frame` 吸收了你说的"框"、"母块"、"Subgraph"、"Group"——它们是同一个东西的不同 formal 状态和不同配置。

## 三、逐个回答你的具体纠结

### Q1：何谓正式与非正式，在后端是定义与存储方式吗？

**不是存储方式的差异，是"有没有契约"的差异。**

| | formal: false | formal: true |
|---|---|---|
| 存哪 | 同一张表 | 同一张表 |
| 有 id 吗 | 有 | 有 |
| 能被引用吗 | 能 | 能 |
| **有契约吗** | **没有** | **有** |
| 进求值吗 | 不进 | 进 |
| 删了会怎样 | 没人管 | 引用它的报 orphan |

**契约 = ports + dtype + eval 这三样中的任意一样。**

所以"正式化"这个动作的本质是：**给一个已存在的 Cell 补上契约字段**。不是"把 A 类型转成 B 类型"。

这也解释了为什么你的复制粘贴场景能成立：副本和原件是同一种数据，只是副本被逐步补了契约。

### Q2：字符串、字符串内联要不要 formal？

不要。**文本内部的片段不是 Cell。**

```
TextCell("流量 Q = 3.5 m³/s")   ← 这是一个 Cell
  ↑ anchor 引用
VarCell(name:"Q", dtype:number) ← 这是另一个 Cell，通过 anchor 指向文本的一段
```

`Q` 这两个字符本身**永远不是对象**，它只是被 VarCell 用 anchor 指着。这样：

- 你改文本，anchor 尝试跟随，失败就 orphan（Var 还在，值还在，只是失去溯源）
- 一段文本可以被 4 个 Var 指（Q、3.5、m³/s、整个式子）
- 不需要在 md 里塞任何标记语法

**你提到的"加中括号或尖括号转义"——不要做。** 那会污染用户的 md，且一旦用户手删了括号，语义就崩了。anchor 是外挂的，md 保持纯净。

### Q3：变量在哪定义？块内还是像 SW 那样专门的地方？

**你的直觉（平级、不该由第一个用它的块负责）是对的，但答案是"两者都要，靠 scope 字段区分"。**

```ts
scope: 'global'        // 全局，任何地方可见（你的"专门定义的地方"）
scope: frameCellId     // 局部，只在这个 frame 内可见（框名.变量名）
scope: nodeCellId      // 私有，节点内部状态（stock/buffer）
```

用户心智：

| 用户在想什么 | 实际发生 |
|---|---|
| "温度这个量整张图都在用" | `scope: 'global'`，在变量面板里列出来 |
| "这个反应器里的停留时间只跟它有关" | `scope: reactorFrameId`，写作 `R1.tau` |
| "这个PID的积分累积值" | `scope: pidNodeId`，外部不可见 |

**关键设计**：变量**不住在**任何块里，它只是**声明了自己的可见范围**。所以"第一个出现它的块不想负责定义它"这个问题不存在——变量是平级的独立 Cell，块只是引用它。

这跟 SW 的全局变量表是同构的，但更灵活（SW 只有全局和零件级两层，你有任意层）。

### Q4：变量能多级嵌套吗？（多维张量）

能，但**嵌套的是类型，不是对象**：

```ts
type DType =
  | { t: 'scalar', unit?: string }
  | { t: 'vector', of: DType, n?: number }
  | { t: 'record', fields: Record<string, DType> }   // ← 流股在这
  | { t: 'stream', of: DType }
  | { t: 'ref', to: CellId }                          // 引用另一个 Var

// 化工流股：
{ t: 'record', fields: {
    T: { t:'scalar', unit:'K' },
    P: { t:'scalar', unit:'Pa' },
    x: { t:'vector', of:{t:'scalar'}, n:5 }
}}
```

**一个 VarCell，一根边，任意深的嵌套。** 不需要"把列向量拖进方括号"这种对象级操作——那是**类型编辑**，在属性面板里改 dtype 就行。

你说的"新建列向量然后新建方括号然后拖进去"是把类型构造当成了空间操作，这会让后端变得极其复杂。**建议：类型用文本/表单编辑，不用拖拽。**

### Q5：框是不是块？要不要同构？

**框是 Cell，节点也是 Cell，它们同构（都是 Cell），但 kind 不同。**

你担心的"grasshopper 里都没这么多骚操作"——GH 确实有：Group（视觉）和 Cluster（封装），就是你的 frame 的两个 formal 状态。

```
FrameCell formal:false  = GH 的 Group / draw.io 的容器
  ├─ 只是个圈
  ├─ 拖动时内容跟着走
  └─ 求值完全无视它

FrameCell formal:true   = GH 的 Cluster / Simulink 的 Subsystem
  ├─ 有 ports（对外接口）
  ├─ 有 namespace（局部变量）
  ├─ 可折叠成一个方块
  └─ 内部是独立的求值域
```

**要不要"子母块"？不需要单独的概念。** formal frame 就是母块，它内部的 node 就是子块。嵌套通过 `parent` 指针，任意深。

**"抓不抓框"**：框自己就是被抓的对象之一。框选一坨 → 生成 FrameCell(formal:false) → 用户觉得它该是个封装了 → 补契约变成 formal:true。**同一个对象，两次操作。**

### Q6：悬空箭头怎么办？

```ts
// 完全合法的边
{ kind:'edge', formal:false, from:cellA, to:null }
```

- `formal: false` 的边：`from`/`to` 可以直接指 Cell（不需要 port），可以为 null
- `formal: true` 的边：必须指 PortRef，但**允许一端悬空**（`to: null` + 提示"未接"）

求值时：悬空边的下游收到 `undefined`，不报错，不阻断其他分支。这跟你场景 1 说的"不会报错而是有提示，其余部分不受影响"完全一致。

### 场景 3：Agent 对话树（这个场景最能暴露设计问题）

你的需求：分支、剪枝、debate、merge、clone 换源重跑、subagent、权限限流。

**关键洞察：对话树的每个节点就是 NodeCell，`eval` 是"调 LLM"。**

```ts
// 一轮对话 = 一个 node
{
  kind:'node', formal:true,
  props:{ role:'assistant', model:'claude-4', agentInstance:'A1' },
  ports:[{name:'context', dir:'in'}, {name:'reply', dir:'out'}],
  eval:{ type:'llm', provider:'anthropic', ... }
}

// 分支 = 从同一个 out port 连出多条 edge
// clone 换源重跑 = 
//   1. 深拷贝子树
//   2. 保留 role:'user' 节点的 value 且 status:'manual'（自动注入）
//   3. role:'assistant' 节点 status 设为 'stale'
//   4. 改 props.model
//   5. tick() → manual 的 user 输入不重算，assistant 全部重跑
```

**注意这里 `status: manual` 的威力**——你之前定的"manual 阻断上游、向下游传 fresh"规则，正好实现了"保留 user 回答、只重跑 agent 回答"。这不是巧合，是同一个机制。

```ts
// debate = 两个分支的 node 互相连边，各自 eval 时能读到对方
// merge = 一个 node 有多个 in edge，eval 时聚合
// 剪枝 = 删子树（或 formal:false 降级为"存档但不跑"）

// 权限限流：
{
  kind:'node', props:{
    agentInstance:'A1',
    quota:{ maxSubagents:3, maxTokens:100000, used:{...} }
  }
}
// 后端在 eval 前检查 quota，超了直接返回 error status
```

**多态继承**：`props.agentInstance` 指向一个 Var（`scope:'global'`，dtype 是 record，存 provider/model/systemPrompt），子节点默认继承父节点的 instance，除非自己覆盖。这就是你说的"有分支则多态继承"。

**挂第三方 agent（opencode/pi）**：`eval:{ type:'external', cmd:'opencode', args:[...] }`。后端起子进程，通过 stdio 交换 JSON。**这需要 HostBridge.exec，浏览器版做不了——这是你第一个真正需要桌面壳的场景。**

## 六、什么时候能敲定？我认为是现在

你说"前端牵制后端因为定义混乱"——上面这套 Cell 模型已经把你所有的纠结吸收了：

| 你的纠结 | 解法 |
|---|---|
| 正式/非正式是什么 | `formal: boolean` 状态位 |
| 块和变量是不是一个东西 | 不是，`kind:'node'` vs `kind:'var'` |
| 框是不是块 | 都是 Cell，`kind:'frame'` |
| 变量在哪定义 | 独立 Cell + `scope` 字段 |
| 变量能否嵌套 | 类型嵌套（DType 递归），不是对象嵌套 |
| 谁能嵌套谁 | 空间嵌套只有 `parent`（frame 装东西）；类型嵌套在 DType |
| 悬空箭头 | `to: null` 合法 |
| 抓的是什么 | 前端宏，展开成 `createCell` + `promote` + `setParent` |

**建议的敲定顺序（今天就能做）：**

1. **写死 `Cell` 的五个 kind 和 `formal` 位** —— 这是地基，写进 `packages/graph-schema`
2. **写死 DType 的递归定义** —— 流股/张量都靠它
3. **写死 Command 列表**（约 12 个）—— agent 和 GUI 共用
4. **写死 status 传播规则** —— 之前已定
5. **暂缓**：anchor 算法细节、eval 的具体协议、tick 的增量优化

**不要等前端想清楚。** 前端的"抓"可以有十种手势，但它们全部展开成上面那 12 个命令。手势怎么设计不影响后端。

## 七、你还没撞上但很快会撞的一个问题

**场景 3 的对话树是"每个节点执行一次就固定"，场景 1/2 的流程图是"每 tick 都重算"。这两种执行语义不同。**

对话树：节点执行完，结果就冻结（除非显式重跑）→ 更像 **一次性 DAG 求值 + checkpoint**
流仿真：每 tick 全部重算 → **周期性求值**

建议加一个字段：

```ts
interface NodeCell {
  evalMode: 'once' | 'reactive' | 'tick'
  // once:     执行一次就冻结（LLM 调用、外部命令）
  // reactive: 上游变了就重算（Grasshopper 式）
  // tick:     每个时间步都算（Simulink 式）
}
```

这三种模式共存于同一张图是完全可能的（一个仿真图里嵌一个 LLM 节点做参数建议），而且这正好覆盖了你之前提到的"节点可挂起/恢复"需求（`once` 模式的节点执行中 → `status: 'pending'`）。

**这个字段现在就加进 schema，比以后重构便宜一万倍。**
